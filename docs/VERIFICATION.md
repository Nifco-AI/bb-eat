## 第 2 轮：Verifier 抓到一个我声称已修复的回归

这是三轮里最有价值的一次发现。

**N-1（HIGH）** — `useOccurredAt` 在 `useState` 初始值里播种日期与时间，而 `FeedingModal`
是常驻挂载的。结果是：控件**看起来**正确，实际冻结在屏幕挂载那一刻的时间。第 1 轮我已声称
修复过"发生时间"相关缺陷，这是同一问题换了形态卷土重来。

- **根因**：把 prop 的默认值**复制**进 state，而组件生命周期长于一次"打开"。
- **修复**：改为**跟随**而非复制 —— `editedDate`/`editedTime` 为 `string | null`，
  未编辑时回落到调用方的实时值；`AppProvider` 增加随 60 秒 tick 重算的 `nowTime`；
  `FeedingModal` 改为条件挂载并以 `${slotId}:${date}` 作 key（顺带修掉了不同餐次之间
  intake mode / 比例 / 克数互相串味的旧问题）。
- **设备实证**：喂食弹窗显示 16:40，一分钟后成长表单显示 16:41。

同轮其余 5 个新缺陷：合成内容可进计划（N-2）、库存选择器未过滤合成（N-3）、
跨午夜停在昨天（N-4）、旧版备份被误报为损坏（N-5）、自指向的导航磁贴（N-6）、
NULL 摄入比例被当成已知的 0（N-7）、迁移静默删除无法归属的行（N-8）、
ErrorBoundary 只包了 3 个 Tab（N-9）。另有 3 处**文案与实现不符**被要求改正。

**`D-5` 的机制性错误**：防连点用的是 React **state**，而 React 会批处理更新，
同一帧内的两次点击都会读到 `busy === false`。改为同步翻转的 **ref**。

## 第 3 轮：Verifier 自己把 WHO 的账算完了

第 1 轮 Verifier 只核对了 2 份 boys 文件，第 3 轮它主动补齐了 girls 的 2 份，
**自行重新下载原始 xlsx、自行实现解析器与逆 LMS 算法**：

- 4 份 xlsx 的 SHA-256 与 `cdn.who.int` **逐字节一致**；
- 每份 1158 行 L/M/S 与打包值逐行一致，最大偏差 `0.0e+00`；
- 逆 LMS 反推 vs WHO 自带 SD 列：8106 次比对，最坏 `0.000500`，超过 `0.001` 的为 **0 个**；
- ±3SD 尾部调整确实只对 `weight_for_age` 生效；超出已发布天数范围时拒绝给分。

这是本项目**唯一证据链完整**的部分，且结论由第三方重算得出，不是自我声明。

同轮发现的 9 个新缺陷中，最重要的是：

**N-15（MEDIUM）** — 我在第 2 轮把合成内容的防线放在 `addPlanItem`，并在提交信息里称其为
"单一卡点"。Verifier 直接绕过 UI 调用仓储层，**成功**把合成食材写进 `recordFeeding` 的
snapshot、`recordExposure`、`recordSuspicion`，以及库存和回避清单的裸 SQL，然后让日小结
把虚构食物报告成"真的吃了"。当前 UI 不会这么做，所以不是线上泄漏，但
`DATA_QUALITY.md` 当时声称"已从所有记录与回避清单中排除"——**数据层并不保证这一点**。

- **修复**：`assertNotSynthetic()` 独立成模块，在 **6 个写入口**全部调用，
  其中 `recordFeeding` 逐条检查 served snapshot。库存与回避清单原本是写在界面组件里的
  内联 SQL（测试、tsc、lint 都够不着），已下沉为仓储函数；选择器查询同样下沉，
  使测试执行的就是界面执行的那条 SQL。
- **新增 4 个回归测试**，每一个在 `97d4430` 上都会失败。

其余：弹窗在午夜被静默重挂载并丢弃半填的夜奶（N-12）、后台无前台刷新导致跨日误判（N-13）、
迁移中止后无逃生路径（N-16）、防连点 ref 在非法时间分支泄漏（N-17）、
